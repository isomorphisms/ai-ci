Owner: [AICI #205](https://github.com/isomorphisms/ai-ci/issues/205).

Continue the retained branch of [isomorphisms/ai-ci PR #210, “Validate Kitchen
mutation attempts from independent API observations”](https://github.com/isomorphisms/ai-ci/pull/210).

`validators/request_delivery.pi` consumes the existing approved FP deployment,
contract, qualification and material/runtime identities. The trusted controller
must select these independently of the candidate/request branch. No second
policy registry is introduced. It compares exact submitted bytes with the
independently selected request and preserves the corrected operation and inputs.
It recomputes source-object, material, checker, runtime, context and delivered-byte
identities. Worker receipts and PASS text cannot replace independent completion
and API postcondition evidence. Cat Food retains sealing ownership.

The checker identity includes same-repository Ithon imports discovered from its
checked syntax tree and pinned source objects. An omitted or replaced helper is
rejected even when the top-level checker and Git HEAD remain unchanged. The
control executable must likewise occur in the approved material manifest.

`check-request-delivery.pi` extends the current `registered_delivery.pi` gate.
It takes, in order: approved configuration, expected
request, actual submitted request, untrusted service result, controller
observations, FP stage, payload, captured response, original human request, and
result path, then (for the current multi-output result) artifact directory and
original submission envelope. The existing registered gate first validates the
complete output pair and intake provenance; the independent supplement then
requires root-owned execution and API observations. Execute through pinned checked Ithon with FP's pinned `handoff.pi`
and AICI validators on the module search path. These inputs are a local trusted
controller interface, not an attestation endpoint for arbitrary caller files.

The delivered-byte contract must be K/R's actual resulting contract in that
approved release. Its operation, kind, filename, context and permitted effects
are bound to the release. Production acceptance requires a maintained paste unit
and observations from the supported caller. A standalone artifact fixture
cannot become production acceptance by changing a status label. The starting
R release does not yet provide that approved contract; missing fields are BLOCKED.

Observed checks must contain every registry-required check, in order, with zero
skips and a request/release binding. Controller capture includes two generations,
two fresh-home/unrelated-directory executions of the identical complete unit,
and raw API fixtures. The reusable `kitchen_transfer.pi` rechecks those raw
observations. A removed check/declaration, changed checker under unchanged HEAD,
lost source, altered runtime/authority, changed parameters, stale cache, unrelated
receipt, fabricated PASS or edited final bytes fails independently.

Evidence reuse is explicit in `reuse`; unchanged approved release/request/output
may reuse qualification. Changed material, checker, dependency, runtime,
environment, registry, delivery contract, source or parameters changes the key.
Final visible delivery always needs a new sink observation. The controller must
never construct independent observations by copying an untrusted result.

`job_delivery.deliver_checked()` wraps the actual maintained FP `handoff.deliver`
and a trusted sink that independently retains the bytes it accepted. It creates
PENDING before calling the sink, checks the capture against the stage and final
payload, and exports PASS only as VERIFIED. The existing delivery CLI likewise
replaces an old PASS before parsing/validation and records BLOCKED, FAILED or
PARTIAL on rejection. A frontend failure before executing these entrypoints must
be handled by the supervising caller using a new attempt path; this module
cannot erase a stale file when it did not execute.
